# Arcus-Lighter 0.1.1：成交确认与历史补账修复

## 已定位的问题

受影响节点的三笔真实历史订单中，Arcus fill.createdAt 分别比订单 createdAt 早 2195、4770、2246 微秒。0.1.0 用订单时间减 1 微秒作为成交查询起点，过滤掉了这些已成交记录，持续返回 UNKNOWN。0.1.1 查询起点向前重叠 60 秒，最终仍按原 orderId、clientId、市场、方向及数量验证归属。

自动对账旧分支只更新仓位 STEP 和 RECONCILED 状态，没有回填成交价格及费用；RECONCILED 又被排除出待对账列表，净价差因此一直为空。

## 修复内容

- Arcus REST 成交查询容忍订单与成交流的时间差；原始终态及完整成交校验保持有效。
- Lighter 等待 WebSocket 时增加 REST 补查，避免丢失回报后固定等完整超时。
- 双腿分别保留执行结果，单腿超时不再覆盖另一腿已经确认的成交。
- 发单前持久化原 client ID；恢复只查原单，不自动重发开仓。
- 对账前补查原成交。双腿完整成交且实际仓位对应准确下一 STEP 时，恢复为成功并回填净价差，重复对账不重复推进 STEP。
- 历史 SUCCEEDED/RECONCILED 但缺少净价差的记录，独立进行只读查单并补账；不改变当前任务 STEP、运行状态或历史成交次数。
- 每腿成交明细与累计结果在同一 SQLite 事务中替换，重复 REST/WS 回报不重复记手续费，也不同时累计临时汇总和真实明细。
- 交易记录增加“补查历史成交”按钮，并把该列表的“净收益”更名为“净价差”。缺少核算信息显示“待核算”。该数值是本次双腿成交的净价差 bps，不是完整开平仓利润。

## 验证与升级

152 项测试通过，包含真实时间偏差回放、迟到回报恢复、重复补账、错误订单身份、成交数量倒退、单腿超时及 API 补账。修复后的适配器只读查询同样三笔真实历史订单，均正确返回 FILLED、成交均价和手续费；验证没有发出订单。

升级前在界面暂停任务，等待正在执行的订单结束。保留节点数据与 2FA；不要使用清除命令。更新后打开节点，检查版本 0.1.1、账户仓位及原 STEP，再继续任务。运行或暂停的已有任务会自动分批补账；已停止任务可使用“补查历史成交”按钮分批补齐。无法取得成交明细的记录仍保持待核算，不按仓位变化猜测成交价格。

版本更新不保证历史记录立即全部补齐，也不把真实未知订单自动标为成功。
